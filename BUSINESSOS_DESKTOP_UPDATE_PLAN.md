# BusinessOS Desktop Update Plan

Version: D8 (0.2.0)

## Current State

BusinessOS currently ships as a standalone NSIS Windows installer. There is no auto-update mechanism. Users must download and run a new installer to upgrade. The `latest.yml` manifest is generated by electron-builder but is not consumed by any update feed.

### What Exists

- electron-builder NSIS packaging (v26.15.3)
- `latest.yml` with version, SHA-512, file size, and release date
- `afterPack` hook ensuring standalone Next.js server is correctly placed
- `postbuild` script staging the standalone build
- Electron 44.2.0

### What Does Not Exist

- Auto-update client (electron-updater not installed)
- Update server / feed URL
- Code signing certificate
- GitHub Releases integration
- Silent/background update flow
- Staged rollout infrastructure
- Update verification beyond SHA-512 in latest.yml

## Recommended Update Architecture

### Phase 1: GitHub Releases (Recommended First Step)

The simplest viable update path uses GitHub Releases as the update feed.

**Components:**
1. **electron-updater** — built into electron-builder, add as dependency
2. **GitHub Releases** — host `latest.yml` and installer executables
3. **Update feed URL** — `https://github.com/{org}/{repo}/releases/latest/download`

**Flow:**
1. App starts → `autoUpdater.checkForUpdates()` → fetches `latest.yml` from GitHub
2. If version > current → download installer in background
3. Prompt user to restart, or schedule silent install on quit
4. NSIS installer replaces existing installation in-place

**Required Changes:**
- Add `"electron-updater"` to devDependencies
- Add `publish` config to package.json `build` section
- Register `autoUpdater` in `desktop/main.cjs`
- Handle `update-available`, `update-downloaded`, `error` events
- Add UI notification for available updates

### Phase 2: Code Signing

Without code signing, Windows SmartScreen will warn users on first install. Code signing eliminates this warning and is required for auto-update to work smoothly.

**Requirements:**
- EV or OV code signing certificate (from DigiCert, Sectigo, etc.)
- `CSC_LINK` and `CSC_KEY_PASSWORD` environment variables for electron-builder
- HSM or cloud key storage for EV certs

### Phase 3: Staged Rollout

For production deployments at customer companies:

- Percentage-based rollout via GitHub Releases (draft → publish)
- Environment variable to override update feed URL per customer
- Customer-specific update channels (stable, beta, enterprise)

## Version Check Flow

```
App Launch
  → app.getVersion() reads package.json version
  → autoUpdater.checkForUpdates()
    → GET https://github.com/{repo}/releases/latest/download/latest.yml
    → Compare version strings (semver)
    → If newer: download BusinessOS-Setup-{version}.exe
    → Verify SHA-512 matches latest.yml
    → Prompt user or schedule silent install
```

## Download Flow

1. electron-updater downloads installer to temp directory
2. Verifies SHA-512 checksum from latest.yml
3. Shows "Update ready" dialog or waits for app quit
4. On install: NSIS detects existing installation, upgrades in-place
5. User data in `%APPDATA%/BusinessOS` is preserved (NSIS `deleteAppDataOnUninstall: false`)

## Verification

- SHA-512 in latest.yml is the primary integrity check
- Code signing verification happens at the OS level (Authenticode)
- No additional verification layer is implemented yet

## Rollback Strategy

Since there is no auto-update yet, rollback is manual:
1. Uninstall current version (preserves user data)
2. Install previous version from archived installer
3. User data and credentials are preserved across versions

When auto-update is implemented:
- Keep previous installer available on GitHub Releases
- `autoUpdater` does not support downgrade; manual reinstall required for rollback
- Consider a `rollbackVersion` environment variable for enterprise customers

## Silent vs Prompted Updates

| Mode | Behavior | Use Case |
|---|---|---|
| Prompted (default) | Show dialog, user clicks "Restart" to install | General release |
| Silent | Install on quit, no dialog | Enterprise-managed deployments |
| Disabled | `autoUpdater.autoDownload = false` | Air-gapped or controlled environments |

## Customer-Safe Rollout

1. Build installer locally
2. Test on internal machine
3. Upload to GitHub Releases as draft
4. Verify SHA-512 and installer integrity
5. Publish release → triggers update check for all users
6. Monitor bootstrap.log for startup failures

## Staged Rollout (Future)

- Use GitHub Releases' draft → published workflow
- First publish to a beta channel (separate feed URL)
- Monitor for 24-48 hours
- Promote to stable channel

## Code Signing Requirements

- **Required for:** Windows SmartScreen bypass, electron-updater signature verification
- **Type:** EV (Extended Validation) recommended for business software
- **Cost:** ~$400-700/year
- **Integration:** Set `CSC_LINK` and `CSC_KEY_PASSWORD` env vars before `electron-builder`
- **Timeline:** Should be obtained before first public release

## Future Considerations

- **Vercel/Next.js role:** The embedded Next.js server is bundled as a standalone build. Updates replace the entire `resources/next` directory. No separate web deployment needed.
- **Database migrations:** Auto-updates do not handle database schema changes. Migrations run automatically via Prisma on server startup.
- **Breaking changes:** Major version bumps should require manual migration or include a migration step in the installer.
